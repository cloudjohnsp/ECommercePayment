# AGENTS.md

## Project overview

This repository contains an independent payment gateway simulator used by the
ECommerce API during local development and integration testing. It exposes an
HTTP API built with Flask, persists payments in PostgreSQL through SQLAlchemy,
and notifies the calling application through signed webhooks.

The simulator owns its payment identifiers and state. It must not access or
modify the ECommerce API database directly.

## Project structure

- `app/__init__.py`: Flask application factory, extension initialization,
  blueprint registration, and the health endpoint.
- `app/config.py`: environment-based application configuration.
- `app/extensions.py`: shared Flask-SQLAlchemy and Flask-Migrate instances.
- `app/models.py`: payment persistence model and payment state transitions.
- `app/routes.py`: HTTP endpoints, request validation, idempotency handling,
  transaction boundaries, and response mapping.
- `app/webhooks.py`: webhook payload creation, HMAC-SHA256 signing, and HTTP
  delivery.
- `migrations/`: Alembic configuration and versioned database migrations.
- `tests/`: pytest fixtures and API behavior tests.
- `wsgi.py`: WSGI entry point used by Flask and Gunicorn.
- `docker-compose.yml`: local API and PostgreSQL services.
- `.dockerignore`: excludes secrets, local environments, caches, tests, and Git
  metadata from the container build context.

## Design and dependency conventions

1. Keep the application factory pattern.
   - Do not create a global Flask application inside the `app` package.
   - Initialize Flask extensions with `init_app` in `create_app`.
   - Keep `wsgi.py` as the composition entry point.

2. Keep responsibilities separated.
   - Models own intrinsic payment state transitions and invariants.
   - Routes handle HTTP concerns, input validation, persistence orchestration,
     and status-code mapping.
   - Webhook signing and delivery belong in `app/webhooks.py`.
   - Configuration must come from `app/config.py` and environment variables.

3. Avoid coupling this service to the ECommerce API implementation.
   - Integration with the ECommerce API occurs only through HTTP requests and
     webhook contracts.
   - Do not import code from the .NET solution or share its database schema.

## Payment behavior

Preserve these business rules when adding or changing features:

- New payments start with status `pending`.
- The public payment identifier is generated by this service and starts with
  `pay_`; the internal UUID is not exposed as the API identifier.
- A pending payment may transition to `approved` or `declined`.
- Repeating the same terminal transition is idempotent and must not deliver a
  duplicate webhook.
- An approved payment cannot be declined, and a declined payment cannot be
  approved. Conflicting transitions return HTTP `409`.
- Monetary values use `Decimal` and `Numeric(18, 2)`, never binary floating
  point for persistence or calculations.
- Timestamps are timezone-aware and recorded in UTC.

## API and idempotency conventions

- `POST /payments` requires the `Idempotency-Key` header.
- Reusing a key with the same normalized request returns the existing payment
  with HTTP `200`.
- Reusing a key with different request data returns HTTP `409`.
- A newly created payment returns HTTP `201`.
- Missing or malformed client input returns HTTP `400` with the existing
  `{ "error": "..." }` response shape.
- Missing resources return HTTP `404`.
- Keep public JSON properties in camelCase and payment statuses lowercase.
- Do not expose database-only fields such as the internal UUID or idempotency
  key in responses.
- Preserve row locking for state transitions so concurrent requests cannot
  apply conflicting changes.

When adding endpoints, use the existing Flask blueprint instead of registering
routes directly in `create_app`, unless the endpoint is application-wide, such
as `/health`.

## Webhook conventions

- Send webhooks only after the payment transaction has committed.
- Events use the names `payment.approved` and `payment.declined`.
- Serialize the payload deterministically before signing it.
- Sign the exact request body with HMAC-SHA256 using `WEBHOOK_SECRET`.
- Put the hexadecimal signature in `X-Payment-Signature`.
- Treat webhook delivery as best effort: a network failure must be logged and
  reported in the transition response, not roll back the payment state.
- Always configure a finite timeout through `WEBHOOK_TIMEOUT_SECONDS`.
- Never log secrets or signature keys.

## Persistence and migrations

- PostgreSQL is the production and Docker Compose database provider.
- Use Flask-SQLAlchemy's shared `db` instance for database access.
- Commit mutations explicitly and roll back the session after database errors.
- Use Alembic/Flask-Migrate for every schema change. Do not rely on
  `db.create_all()` outside tests.
- Keep model definitions and migration definitions aligned, including enum
  values, nullability, lengths, indexes, and unique constraints.
- Do not edit a migration that may already have been applied. Add a new
  migration instead.
- Retain database uniqueness constraints for `external_id` and
  `idempotency_key`; application checks alone are not sufficient under
  concurrency.

## Configuration and security

- Do not commit `.env`, credentials, webhook secrets, or connection strings
  containing real passwords.
- Add new settings to `Config`, document them in `.env.example`, and pass them
  through `docker-compose.yml` when containers require them.
- No webhook secret or database password has a runtime default; startup must fail
  when required configuration is missing.
- Validate callback URLs before persisting them. If this simulator is ever
  exposed outside a trusted development environment, add SSRF protections
  before allowing arbitrary webhook destinations.

## Testing conventions

- Use pytest and Flask's test client for API behavior tests.
- Tests use an isolated in-memory SQLite database unless a behavior specifically
  requires PostgreSQL semantics.
- Mock outbound webhook requests; tests must not make real network calls.
- Test observable behavior rather than implementation details.
- Add or update tests for success, validation failure, not-found, conflict,
  idempotency, and webhook behavior when changing an endpoint.
- For persistence behavior that depends on row locks, PostgreSQL types, or
  concurrent transactions, add an integration test against PostgreSQL rather
  than assuming SQLite behaves identically.

## Local validation

Run the unit/API test suite:

```bash
pytest
```

Run the service and PostgreSQL together:

```bash
docker compose up --build
```

Apply migrations during local development:

```bash
flask --app wsgi db upgrade
```

When a schema change is required, create and inspect a migration before
applying it:

```bash
flask --app wsgi db migrate -m "describe the change"
flask --app wsgi db upgrade
```

## Agent guidelines

- Preserve the external API contract unless the requested change explicitly
  requires a breaking change.
- Prefer small, focused changes that follow the existing module boundaries.
- Add a regression test before fixing a reported behavior defect when
  practical.
- Do not replace `Decimal`, remove idempotency guarantees, weaken database
  constraints, or move webhook delivery before the commit.
- Keep Docker, environment examples, migrations, tests, and README instructions
  synchronized with runtime changes.
- Do not modify the neighboring ECommerce API repository unless the task
  explicitly includes both services.
